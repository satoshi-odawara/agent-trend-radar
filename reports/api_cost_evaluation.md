# データ収集のAPIコスト評価レポート

**調査日**: 2026-09-07
**調査範囲**: `scripts/collect.py`によるGitHub APIデータ収集のコスト構造
(特にAPI実行回数制限に対する余裕度)
**調査対象**: `config/targets.yaml`記載の全20リポジトリに対する1回分の
収集実行
**方針**: 実装(`checks.py`, `agent_doc_analysis.py`, `github_client.py`)は
変更せず、現行コードの実行結果を実測とコード解析で評価するのみ。

## 方法論

- GitHub APIのレート制限消費は、実際のContents APIレスポンスヘッダー
  (`x-ratelimit-used` / `x-ratelimit-remaining`)を`collect.py`実行の前後で
  直接比較して実測した。
  - 専用の`/rate_limit`エンドポイントは、この調査を行った実行環境では
    リクエストを重ねても値が更新されない(キャッシュされた古い値を
    返し続ける)挙動が確認され、信頼できなかったため使用しなかった。
    実際のAPIコール(Contents API)のレスポンスヘッダーは値が正しく
    変化することを確認済み。
- `checks.py`/`agent_doc_analysis.py`の各チェック関数が何回GitHub APIを
  呼ぶかをコードから静的に確認し(短絡評価`any()`の挙動も含む)、理論値を
  算出したうえで実測値と突き合わせた。

## 実測結果

| 項目 | 値 |
|---|---|
| 対象リポジトリ数 | 20 |
| 実行時間 | 1分12秒 |
| 消費APIコール数(実測) | 233コール |
| 平均コール数/リポジトリ | 約11.65コール |
| 認証PATのレート制限 | 5,000コール/時(レスポンスヘッダーで確認) |
| 消費率 | 4.7%(233 / 5,000) |

事前にコードから算出した理論値(約230コール、内訳:
has_agent_instructions 1〜3、has_tests 1、has_eval 1〜2、has_ci 1、
has_security_policy 1、has_observability_dep 3、CLAUDE.md/AGENTS.md
内容取得2)とほぼ一致し、コードの呼び出しパスの見積もりが正確だった
ことを確認した。

## 評価観点ごとの結果

### 1. 1回の収集実行あたりのAPI呼び出し回数
実測233コール/20リポジトリ。事前推定とほぼ一致。

### 2. レート制限に対する余裕度
233 / 5,000(認証PAT・1時間あたり)= **4.7%**。実測でも極めて余裕がある。

### 3. 対象リポジトリ数のスケーラビリティ
233コールを20件から線形計算すると:

| 対象件数 | 推定コール数 | 認証PAT(5,000/h)に対する割合 | Actions既定トークン(1,000/h)に対する割合 |
|---|---|---|---|
| 20(現状) | 233 | 4.7% | 23.3% |
| 50 | 約583 | 11.7% | 58.3% |
| 100 | 約1,165 | 23.3% | **116.5%(超過)** |
| 200 | 約2,330 | 46.6% | 233%(超過) |

PAT運用なら200件規模まで1時間1回の実行で問題ない。ただし#10で
GitHub Actions既定の`GITHUB_TOKEN`(公式仕様上1,000/時、本調査では
未実測)を使う場合、対象が100件を超えると1回の実行で使い切る計算になる。

### 4. 重複・無駄コールの有無
`has_agent_instructions`(存在確認)と`fetch_agent_doc_content`(内容取得)
が、CLAUDE.md/AGENTS.mdという同じパスに対して別々にAPIを叩いている。
存在確認時の取得結果を使い回せば、1リポジトリあたり最大2コール
(20リポジトリで約40コール、実測233の約17%相当)を削減できる余地がある。
現状の余裕を踏まえると緊急の最適化ではないが、対象リポジトリ数が
増えた際の低コストな改善候補として記録する。

### 5. 失敗時のリトライ設計の有無
`collect.py`は`GitHubClientError`発生時に該当リポジトリをスキップして
次に進む設計であり、無駄なリトライによるコール浪費は現状発生しない。
ただし週次自動実行(#10)でレート制限に達した場合、そのリポジトリの
データは前回分のまま更新されず欠損が蓄積する。#11で扱うべき論点として
引き続き有効。

### 6. 実行頻度との掛け算(週次cron前提)
週次運用(233コール/週)なら無視できるレベル。開発中に手動で何度も
再実行しても、PAT運用なら理論上1時間に約21回実行できる計算
(5,000 ÷ 233)で、通常の開発フローでレート制限に達することはまずない。

### 7. 金銭コスト
GitHub API自体は無料。本リポジトリはOSS公開前提(パブリックリポジトリ)
のため、GitHub Actionsの実行時間も無料枠で収まる想定(実測1分12秒/回)。
将来の#15(LLMによる内容分析)は別軸のコストであり、本調査の対象外。

## 結論

現状の対象規模(20リポジトリ、週次実行)では、GitHub APIの実行回数制限は
事実上ボトルネックにならない(認証PATの4.7%しか消費しない)。懸念が
生じるのは「#13で対象を100件以上に拡大」かつ「#10でGitHub Actions既定
トークンを使う」の両方が重なった場合のみであり、現時点で対応を急ぐ
必要はないと判断する。
