# データ有効性・妥当性検証タスク(Claude Project用)

このチャットスペースの役割は「収集済みデータからの考察」のみです。
実装コード(`src/`, `tests/`等)はこのフォルダの外にあり、意図的に
同期対象から外しています(理由: Claude Codeでの実装作業と、この
考察作業のコンテキストを混ぜないため。詳細な経緯はagent-trend-radar
リポジトリのIssue #12参照)。**このチャットで実装コードの修正や
Issueの起票そのものは行わず、発見事項の言語化に留めてください。**
リポジトリ側への反映が必要な場合は、その旨をユーザーに伝えてください。

## このフォルダのデータ構成

- `report.md`: 対象20リポジトリ×21項目(ファイル存在5項目、ルール
  ベース内容分析8項目、LLM内容分析4項目、他)のマトリクス表
- `stats.md`: 上記21項目をsegment(tool/adopter)×monetization_model
  (commercial_saas/big_corp_internal/nonprofit_foundation/
  individual_community)でグループ化した統計。数値項目はmin/median/
  mean/max、真偽値項目はn/true件数/true率
- `agent_docs/<owner>__<repo>.md`: 20リポジトリ中16リポジトリが実際に
  保有するCLAUDE.md/AGENTS.mdの生テキスト全文(要約・抜粋はしていない)

すべて機械的な収集結果であり、この文面自体を含めてリポジトリ側で
要約・解釈は行っていません。解釈はこのチャットの仕事です。

## 解釈上の注意点(必ず踏まえること)

以下はこのプロジェクトが過去に実際に誤りかけた事例からまとめたもの
です(元資料: リポジトリの`reports/analysis_interpretation_caveats.md`、
Issue #17)。

1. **平均値だけで語らない**: 平均は外れ値に弱い(例:
   `agent_doc_char_count`のcommercial_saas平均23,275字は
   OpenHands/OpenHandsという1件の外れ値(120,034字)に強く引っ張られ、
   中央値は12,202字だった)。`stats.md`のmedian/mean両方を見て、
   乖離が大きい場合は外れ値の影響を疑うこと。
2. **segment間比較は選定バイアスを疑う**: 対象リポジトリの選定基準
   自体が、一部の項目の分布を最初から決めてしまっている
   (例: `has_agent_instructions`は、adopterセグメントを選ぶ基準が
   「CLAUDE.md/AGENTS.md等の採用が公知の事例」であるため、adopterが
   最初から高い値になるよう選ばれている)。tool内部だけで
   monetization_model別に見る、のように選定基準に汚染されていない
   軸を優先すること。
3. **天井/床効果のある項目は比較材料にならない**: ほぼ全件が同じ値
   (0%/100%付近)の項目は、差を語る根拠にならない(例: `has_ci`は
   adopter 100%・tool 90%とほぼ天井に張り付いている)。

## 検証タスク

### タスクA: 各項目の弁別力の棚卸し

`stats.md`を見て、21項目それぞれについて「segment×monetization_model
間で意味のある差(分散)があるか」を判定してください。天井/床効果に
陥っている項目(候補: `has_ci`、`agent_doc_has_code_block`。すでに
リポジトリ側でIssue #20として認識済み)と、実際に弁別力のある項目を
分けて一覧化してください。

### タスクB: LLM分類(4項目)の信頼性スポットチェック

`report.md`の`agent_doc_mentions_repo_structure` /
`agent_doc_mentions_boundaries` / `agent_doc_mentions_pr_review` /
`agent_doc_mentions_release_process`について、2〜3リポジトリを選び、
`agent_docs/`内の該当する生テキストを実際に読んで、判定値(true/false)
が本文の記述と整合しているかを確認してください。整合しない、あるいは
判断が難しいケースがあれば具体的に指摘してください。

### タスクC: 「AIエージェント運用のベストプラクティス」を語れるか

このプロジェクトの目的(AIエージェントツールが実際のソフトウェア開発で
どう使われているかをエビデンスで示す)に照らして、現在のデータで
どこまで踏み込んだ主張ができるか評価してください。特に以下の限界を
踏まえること。

- 全項目が「ルールの整備状況(有無)」のシグナルであり、それが実際に
  機能しているか(アウトカム)は測っていない
- 各リポジトリ1時点のスナップショットであり、時系列の変化は見えない
- `agent_docs/`の生テキストはあるので、個別リポジトリの「どう書いて
  いるか」という一次情報からの定性的な考察は可能(ただし複数リポジトリ
  を横断した一般化には注意)

主張したい内容に対してデータが不足している場合は、何が足りないかを
具体的に言語化してください(例: 「PRレビューの実効性を語るには
`agent_doc_mentions_pr_review`だけでは不十分で、実際のPRレビュー
履歴データが要る」等)。

### タスクD: 発見のまとめ

タスクA〜Cの結果を踏まえ、以下を整理してください。

1. 現時点のデータで自信を持って言える示唆(根拠となる項目・数値付き)
2. 言えそうだが注意が必要な示唆(バイアス・弁別力の限界を明記)
3. 今のデータでは言えないこと・データが足りない点

3については、リポジトリ側で新しいIssueとして検討する価値があるかを
一緒に判断できるよう、ユーザーに持ち帰ってもらう形で構いません。
